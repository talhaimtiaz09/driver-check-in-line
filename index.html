Workflow A: Driver Check-In Line

2026-10-29 · Talha Imtiaz

Use case

Truck drivers call their broker several times a day to report where they are, and dispatchers spend hours on these calls. Sam, the voice agent on the Ridgeline Freight check-in line, looks up the load and works out the remaining drive time from public map APIs. It then tells the driver whether they will make the delivery appointment and logs the check-in, with a priority and a draft customer notice, for dispatch.

High-level flow

  1. Web call: the driver calls in. Sam asks for the load number and reads it back digit by digit to confirm it.

  2. get_load tool: looks up the load in a mock TMS and returns the delivery address and appointment time. If the load isn't found, Sam asks once more, then promises a dispatcher callback.

  3. drive_time tool: geocodes the driver's city with Open-Meteo, gets the remaining drive time from OSRM, and a code step compares it with the time left before the appointment: on time, at risk (under 60 min to spare) or late.

  4. The API result steers the call: if the driver is on track, Sam reads back the ETA. If late, Sam asks for the reason and a new ETA. If the city can't be found or routing fails, Sam asks for the driver's own ETA and never guesses.

  5. After the call: Extract pulls the load number, driver, location, ETA and delay reason. Classify labels the call on time, at risk, late, breakdown, accident or unverified. Generate writes a priority (P1–P4), the dispatcher's next action and a customer notice.

  6. Write-back: one row per call goes to the load_check_ins table in Twin, with the extracted fields, the system's verdict, the classification and the ops notes.

Components used

  • Inbound Voice Agent: Sam, a single fixed voice, with a transcriber hint for 5-digit load numbers

  • Web call trigger only: no phone number bought, no outbound calls

  • 2+ tool calls: get_load and drive_time

  • Public API call, result used in the flow: Open-Meteo geocoding and OSRM routing; their drive time decides on time, at risk or late, and that decides what Sam says next

  • AI node: Generate, which writes the priority, next action and customer notice

  • Classify node: load status (6 classes)

  • Extract node: check-in details (5 fields)

  • Write-back node: Write to Twin, load_check_ins table

  • Code steps (Python Sandbox): mock TMS lookup, the on-time/late decision, and formatting the tool results for the agent

Design

The on-time or late verdict comes from code using the routing API's drive time, not from the LLM, so the same load and city always give the same answer. Sam may only state times a tool returned, and every failure has a path that falls back to the driver's own ETA or a dispatcher callback, so the agent never invents a number.
